# 电商套图生图规划

本文档只描述设计和开发规划, 当前不代表功能已经实现.目标是让用户上传多张产品图后, 先由视觉模型提取产品信息并生成一组镜头提示词, 再由生图模型按镜头生成 5-6 张套图, 最后由视觉模型统一复核.视觉复核只产出评估结果, 不自动触发重新生成.

## 一. 目标与边界

### 目标

- 支持上传多张产品原图, 保留图片顺序、文件名和用户标注用途.
- 先使用多模态视觉模型分析产品, 形成可复用的产品档案.
- 根据产品档案、选定风格和镜头模板生成 5-6 条独立提示词.
- 每个镜头独立调用生图模型, 允许单镜头状态、失败原因和耗时单独展示.
- 生成完成后, 将产品原图和生成图上传给视觉模型进行整套复核.
- 视觉复核上传时只压缩生成图, 产品原图保持原始版本.
- 复核后保留生成原图, 支持原图下载、ZIP 导出、保存到素材和导入画布.
- 复核结果和每张图片的提示词、模型、尺寸、耗时可以再次查看.

### 明确不做

- 不覆盖或替换用户上传的产品原图.
- 不覆盖生图模型返回的生成原图.
- 不把压缩图作为用户最终下载版本.
- 不根据视觉模型的复核结论自动重新生成.
- 不在第一期实现服务端长期任务队列或关闭浏览器后继续运行.
- 不因为视觉复核失败而静默改用未压缩生成图继续上传.

### 核心不变量

```text
产品原图只用于产品分析、生图参考和复核参考.
生成原图只用于本地正式保存和最终交付.
生成压缩图只用于视觉复核请求, 生命周期不超过复核任务.
视觉复核只改变 review 状态, 不改变 generation 结果.
```

## 二. 端到端流程

```text
创建套图任务
    |
    v
上传产品原图并排序、标注
    |
    v
视觉模型分析产品档案
    |
    v
生成并展示 5-6 个镜头提示词
    |
    v
用户确认或编辑提示词
    |
    v
按镜头生成图片, 每张完成后立即保存原图
    |
    v
生成图临时压缩, 产品原图保持原样
    |
    v
视觉模型复核整套图片
    |
    v
展示通过或人工确认状态, 不自动重生成
    |
    v
原图下载、ZIP 导出、保存素材、导入画布
```

### 1. 创建任务

优先在现有 `/image` 页面中增加模式切换:

- 单图生成.
- 电商套图.

不新增独立营销页, 继续使用现有生图工作台的主题、模型配置和日志布局.

进入电商套图模式后, 用户可以设置:

- 套图名称.
- 产品参考图.
- 视觉风格预设.
- 镜头数量和镜头顺序.
- 全局提示词和禁止项.
- 生图模型、质量、尺寸和背景配置.

### 2. 上传产品原图

每张产品图记录以下信息:

- `id`.
- `name`.
- `order`.
- `role`, 例如主图、包装、细节、尺寸参考.
- `storageKey`.
- `width`、`height`、`bytes`、`mimeType`.

产品原图直接使用现有图片存储能力保存, 不在上传阶段替换成压缩版本.这样可以保证后续分析和复核仍然能看到完整的产品细节.

### 3. 视觉模型生成产品档案

视觉模型收到产品原图和一个固定分析指令, 返回结构化的产品档案.建议字段如下:

```ts
type ProductProfile = {
    productName: string;
    category: string;
    shape: string;
    materials: string[];
    colors: string[];
    surfaceDetails: string[];
    packagingDetails: string[];
    visibleText: string[];
    mustKeep: string[];
    mustAvoid: string[];
    usageNotes: string[];
};
```

分析指令必须要求模型区分“看得到的事实”和“推测内容”.产品形状、材质、包装、logo、标签文字、颜色和结构层次应优先写入 `mustKeep`.模型无法确认的内容不能写成确定事实.

现有 `requestImageQuestion` 已经支持文本和图片消息, 第一阶段可以继续使用当前 `textModel` 中具备视觉输入能力的模型.后续如果模型渠道明确区分文本模型和视觉模型, 再增加单独的 `visionModel` 配置.

模型返回内容应优先要求 JSON.当前请求层是流式文本返回, 因此需要增加显式 JSON 解析和校验:

- JSON 解析失败时, 任务进入“分析失败”.
- 字段缺失时, 任务进入“分析结果不完整”.
- 不允许静默使用空对象或原始自由文本继续生成.
- 用户可以查看分析结果后重新执行分析.

### 4. 生成套图提示词

提示词规划模型接收:

- `ProductProfile`.
- 用户选择的风格预设.
- 全局提示词.
- 镜头模板.
- 文字和构图要求.

建议一次生成完整的 `PromptPlan`, 便于用户在生图前统一检查:

```ts
type PromptPlan = {
    globalConstraints: string[];
    slots: Array<{
        id: string;
        role: string;
        title: string;
        prompt: string;
        size?: string;
        requiredElements: string[];
        avoidElements: string[];
    }>;
};
```

每条镜头提示词由三层组成:

```text
产品一致性约束
+ 风格和品牌视觉约束
+ 当前镜头的主体、构图、镜头、光线和文字要求
```

第一期可内置以下镜头模板:

1. 系列首图.
2. 材质或细节微距.
3. 产品使用场景.
4. 核心卖点展示.
5. 包装、尺寸或规格展示.
6. 收尾图或活动图.

用户可以关闭某个镜头, 调整顺序或编辑单个提示词.编辑后的提示词应成为实际生图请求的唯一来源, 不能在请求层再次拼接出第二份不可见提示词.

## 三. 生图任务设计

### 1. 每个镜头独立请求

不使用一个 `n=6` 请求生成整个套图, 而是每个镜头单独调用一次 `count=1`:

- 每个镜头有独立提示词.
- 每个镜头可以使用独立比例或尺寸.
- 单张失败时只影响当前镜头.
- 可以准确记录每张图的模型参数和耗时.
- 视觉复核结果可以和具体 `slotId` 对应.

### 2. 并发与内存

默认并发上限为 2-3 个镜头.当前图片工作台使用并行任务生成多个结果, 套图模式需要使用有上限的任务队列, 避免 5-6 张 2K 图片同时占用大量浏览器内存和网络连接.

每个镜头的处理顺序应为:

```text
请求生成
-> 读取返回图片
-> 立刻写入 image_files
-> 只把 storageKey 和元数据写入任务状态
-> 释放 data URL 和临时 Blob 引用
```

React 状态中不长期保留 6 张完整 base64 图片.预览组件通过 `storageKey` 懒加载对象 URL.

### 3. 任务状态

任务状态建议为:

```ts
type EcommerceSetStatus =
    | "draft"
    | "analyzing"
    | "prompt_ready"
    | "generating"
    | "generated"
    | "reviewing"
    | "reviewed"
    | "partial"
    | "failed"
    | "cancelled";

type EcommerceSlotStatus =
    | "pending"
    | "generating"
    | "generated"
    | "generation_failed"
    | "review_pending"
    | "passed"
    | "manual_review";
```

“复核不通过”不能直接映射为“重新生成”.复核结果只能进入 `manual_review`, 并保留具体问题.后续是否允许用户手动发起新版本, 作为独立需求处理.

## 四. 视觉复核与压缩边界

### 1. 复核请求内容

视觉复核请求包括:

- 产品原图 1 到 N, 保持原始版本.
- 生成图 1 到 6, 使用临时压缩版本.
- 文字说明, 明确每张图片的 `slotId`、角色和顺序.
- 固定复核规则.

复核规则至少覆盖:

- 产品外观是否和参考图一致.
- 产品结构、颜色和材质是否被错误改变.
- 构图和镜头是否符合当前角色.
- 生成图片中的文字、logo、包装信息是否清晰且正确.
- 是否出现额外产品、重复主体、变形、缺失或遮挡.
- 整套图片的风格、色彩和视觉层级是否统一.

### 2. 只压缩生成图

压缩发生在视觉复核服务入口, 不修改通用 `uploadImage()` 行为:

```text
产品原图: original data URL 或原始 Blob
生成图: original Blob -> compressForVisionReview() -> review Blob
```

压缩策略:

- 默认编码质量为 `0.8`.
- 默认保持宽高不变.
- 优先 WebP, 不支持透明时才使用 JPEG.
- 透明图不能强制转成 JPEG.
- 压缩后读取实际 `Blob.size`, 在任务详情中记录复核请求体积.
- 压缩失败时阻止本次复核, 不自动上传未压缩生成图作为兜底.

这里的 `0.8` 是编码质量目标, 不是严格保证文件体积变成原来的 80%.不同图片内容的压缩比例会不同.

### 3. 临时生命周期

视觉复核压缩图不应成为正式资产:

- 优先只保留在当前任务内存中.
- 不写入 `image_files` 的正式图片记录.
- 不生成可被素材、画布或 WebDAV 识别的正式 `storageKey`.
- 复核结束后释放 Blob、Data URL 和对象 URL.
- 页面刷新后不恢复压缩副本, 只恢复原始生成图和复核结论.

当前 `web/src/services/app-sync.ts` 会递归收集数据中的媒体 key. 如果后续确实需要缓存复核压缩图, 应使用独立的 `review-cache` 仓库和非同步 key, 不能复用 `image:` key.

### 4. 复核响应

视觉模型返回结构化复核报告:

```ts
type EcommerceReview = {
    reviewedAt: number;
    status: "passed" | "manual_review" | "failed";
    summary: string;
    slots: Array<{
        slotId: string;
        status: "passed" | "manual_review";
        confidence?: number;
        checks: {
            productConsistency: boolean;
            materialAccuracy: boolean;
            composition: boolean;
            textAccuracy: boolean;
        };
        issues: string[];
    }>;
};
```

如果一次复核的图片数量或请求体积超过当前模型限制, 可以按镜头分批复核, 但每一批都必须包含产品原图, 并明确显示“分批复核”.不能静默丢弃参考图或生成图.

## 五. 数据模型与持久化

建议把电商套图任务作为现有图片生成日志的一种记录类型, 不新建第二套无法互相理解的生成事实源.现有 `image_generation_logs` 可以增加 `kind` 和套图字段, 旧记录默认为 `single`.

```ts
type ImageGenerationRecord = {
    id: string;
    kind: "single" | "ecommerce-set";
    title: string;
    createdAt: number;
    updatedAt: number;
    status: EcommerceSetStatus | "success" | "failed";
    model: string;
    config: GenerationLogConfig;
    references: ReferenceImage[];
    productProfile?: ProductProfile;
    promptPlan?: PromptPlan;
    slots?: EcommerceSetSlot[];
    review?: EcommerceReview;
};

type EcommerceSetSlot = {
    id: string;
    order: number;
    role: string;
    title: string;
    prompt: string;
    status: EcommerceSlotStatus;
    originalStorageKey?: string;
    naturalWidth?: number;
    naturalHeight?: number;
    bytes?: number;
    mimeType?: string;
    durationMs?: number;
    error?: string;
    attempts: number;
};
```

持久化规则:

- `references` 只保存参考图元数据和原始 `storageKey`.
- `slots` 只保存生成原图的 `originalStorageKey` 和元数据.
- `review` 只保存复核报告, 不保存复核上传副本.
- 有 `storageKey` 时不持久化完整 `dataUrl`.
- 删除套图记录时, 只清理不再被资产、画布或其他日志引用的原始图片.
- 现有单图日志读取时补齐 `kind: "single"`, 不影响旧记录.

保存到“我的素材”时, 资产 metadata 增加:

```ts
{
    source: "ecommerce-set",
    setId: "...",
    slotId: "hero",
    role: "系列首图",
    stylePresetId: "...",
    prompt: "..."
}
```

这样 6 张图片可以独立使用, 同时仍然能追溯到原始套图任务.

## 六. 页面与交互规划

### 左侧: 任务与历史

- 显示套图名称、风格、数量、状态、更新时间.
- 任务卡片显示 4 张以内缩略图和整体状态.
- 支持新建、打开、删除和继续查看.
- 任务运行中显示已完成数量和当前阶段.

### 中间: 输入与提示词

- 产品参考图横向排列, 显示顺序和角色.
- 允许拖拽调整顺序.
- 显示产品分析结果, 支持重新分析.
- 风格预设使用选择卡片, 同时支持自定义风格说明.
- 镜头提示词按顺序展示, 支持启用、禁用、编辑和排序.
- 生图前显示完整请求摘要, 让用户能确认产品约束和文字要求.

### 右侧: 结果与复核

- 结果按照镜头角色显示, 不只显示“生成结果 1”.
- 每个镜头独立显示生成中、成功、失败和复核状态.
- 预览使用原图对象 URL, 列表缩略图可以按需生成 UI 缩略图.
- 复核完成后显示通过、需人工确认和具体问题.
- 提供下载原图、批量 ZIP、保存到素材和发送到画布.

### 视觉风格

继续沿用当前画布主题和工作台布局, 使用紧凑的操作型界面.不要新增营销式 Hero 或装饰性大卡片.关键操作优先使用图标加文字, 复核状态使用稳定的颜色和文字同时表达, 避免只依赖颜色.

## 七. 建议的代码边界

第一期建议按以下职责拆分, 避免继续把所有状态堆进 `web/src/pages/image/index.tsx`:

```text
web/src/types/ecommerce-set.ts
  ProductProfile, PromptPlan, EcommerceSetSlot, EcommerceReview

web/src/lib/ecommerce-set/presets.ts
  风格预设和镜头模板

web/src/lib/ecommerce-set/prompt-plan.ts
  分析结果校验、提示词计划校验和提示词拼装

web/src/lib/image-compression.ts
  仅提供视觉复核上传所需的 Blob 压缩能力

web/src/services/ecommerce-set-generation.ts
  产品分析、提示词规划、并发生成、复核任务编排

web/src/stores/use-ecommerce-set-store.ts
  当前任务状态、槽位状态和任务动作

web/src/pages/image/components/
  套图输入、提示词列表、镜头结果、复核摘要等页面私有组件
```

服务层需要复用现有能力:

- `requestImageQuestion` 用于产品分析、提示词规划和视觉复核.
- `requestEdit` 用于带产品参考图的镜头生成.
- `uploadImage` 用于正式原图保存, 不在其中增加默认压缩.
- 现有 `image_generation_logs` 用于持久化任务记录.
- 现有素材和画布导出能力用于最终交付.

## 八. 分阶段开发计划

### 阶段 0: 契约和存储设计

- 抽取现有图片生成日志类型.
- 增加 `kind: "single" | "ecommerce-set"`.
- 确定 `originalStorageKey` 和任务引用清理规则.
- 确定旧日志归一化规则.
- 确定视觉分析、提示词计划和复核 JSON 契约.

完成标准: 不修改现有单图生成行为, 新旧日志可以分别读取.

### 阶段 1: 产品分析和提示词计划

- 增加套图模式入口和任务草稿.
- 接入产品视觉分析.
- 增加产品档案展示和编辑.
- 增加风格预设和 5-6 个镜头模板.
- 接入提示词规划并允许用户修改.

完成标准: 在不调用生图的情况下, 用户可以生成、检查并保存一份完整的提示词计划.

### 阶段 2: 镜头生成队列

- 按镜头独立调用 `requestEdit`.
- 增加 2-3 个并发 worker.
- 每张成功图片立即保存原始 Blob.
- 增加单镜头失败状态、错误详情和停止任务.
- 页面刷新后恢复已完成的原图和未完成状态.

完成标准: 6 个镜头可以部分成功, 不会因为一张失败丢失其他结果, 不会把所有大图长期放在 React state 中.

### 阶段 3: 视觉复核和临时压缩

- 实现 `compressForVisionReview`.
- 只压缩生成图, 产品原图保持原样.
- 组装带 `slotId` 和角色说明的多模态复核请求.
- 保存复核报告, 不触发重新生成.
- 复核完成后释放临时压缩数据.

完成标准: 复核请求中可以验证产品图是原始版本, 生成图是压缩版本, 请求失败时不会偷偷上传未压缩图, 复核报告和槽位一一对应.

### 阶段 4: 交付和画布集成

- 批量下载原始生成图.
- 导出包含原图和任务 manifest 的 ZIP.
- 批量保存到“我的素材”, 写入 `setId` 和 `slotId`.
- 一键发送到画布, 创建 5-6 个原图节点并保持顺序.
- 删除任务时执行原图引用清理.

完成标准: 用户下载和画布中看到的都是原始生成图, 不是视觉复核压缩副本.

### 阶段 5: 同步和 Agent 扩展

- 检查现有 WebDAV image-workbench manifest 对套图字段的兼容性.
- 确保复核临时数据不进入 WebDAV 文件清单.
- 增加套图任务读取和状态查询.
- 后续再考虑 Agent 通过结构化参数创建套图任务.

完成标准: 跨设备同步的是任务元数据和正式原图, 不同步临时复核压缩图.

## 九. 错误处理和恢复

### 产品分析失败

- 显示真实的模型或 JSON 校验错误.
- 不创建可运行的空提示词计划.
- 允许用户重试分析.

### 提示词规划失败

- 保留产品档案.
- 不开始生图.
- 允许重新规划或手动补齐缺失镜头.

### 部分镜头生成失败

- 成功镜头保留原图和状态.
- 失败镜头显示错误和尝试次数.
- 任务整体标记为 `partial`.
- 不清除已经成功的镜头.

### 视觉复核失败

- 保留所有生成原图.
- 任务标记为复核失败, 而不是生成失败.
- 显示压缩、请求体积或模型返回的具体错误.
- 不自动改用未压缩图片重新请求.

### 用户停止任务

- 中断尚未开始或正在请求的镜头.
- 已完成原图继续保留.
- 任务进入 `cancelled` 或 `partial`.
- 后续恢复时只处理未完成镜头, 不重复生成已经成功的镜头.

## 十. 验证计划

### 单元测试

- 产品档案 JSON 的解析、字段校验和非法字段处理.
- 提示词计划的镜头数量、唯一 `slotId` 和顺序校验.
- 压缩函数保持原始宽高.
- JPEG、WebP、PNG 透明通道的格式选择.
- 压缩结果包含真实 `Blob.size` 和正确 MIME 类型.
- 任务状态从分析、生成到复核的合法转换.
- 旧单图日志归一化为 `kind: "single"`.

### 集成测试

- 上传多张产品原图后, 分析请求按原始版本发送.
- 生成请求使用产品参考图和单镜头提示词.
- 6 个镜头中部分失败时, 成功镜头原图仍然存在.
- 复核请求使用产品原图和生成压缩图.
- 复核请求中不能出现生成原图的完整 data URL.
- 视觉模型返回复核结论后, 不再调用 `requestEdit` 或 `requestGeneration`.
- 删除任务不会删除仍被素材或画布引用的生成原图.
- WebDAV 文件清单不包含复核临时压缩图.

### 浏览器人工验收

- 真实上传 3-5 张产品图, 能正确显示顺序和角色.
- 产品档案中的材质、颜色、包装和可见文字与原图基本一致.
- 提示词计划能完整显示 5-6 个镜头, 修改后实际请求内容同步变化.
- 生成期间可以看到每个镜头的独立状态.
- 生成图片较大时, 视觉复核请求体积明显小于直接上传 6 张原图.
- 视觉复核结束后, 下载的图片尺寸、格式和字节大小对应生成原图.
- 复核标记为人工确认时, 页面不自动重新生成.
- 刷新页面后, 原始生成图和复核报告仍可恢复.

## 十一. 风险和待确认项

- `quality = 0.8` 是编码质量参数, 不能保证所有图片都达到固定字节压缩比例.
- 不同视觉模型对一次请求中的图片数量、单图大小和总请求大小有不同限制, 需要在实际渠道上验证并显示明确错误.
- 产品原图包含隐私、包装信息或未公开素材时, 仍会被发送到用户配置的视觉和生图服务, 需要在页面上保留清晰的隐私提示.
- 浏览器关闭后, 第一阶段不能保证正在进行的视觉分析、生图或复核任务继续运行.
- 如果未来需要降低生图服务本身的计算或响应成本, 仅压缩复核上传图不够, 还需要调整生图尺寸或增加服务端代理转码.
- 是否允许用户在复核后手动重新生成新版本, 不纳入本规划的自动流程, 需要单独确认交互和版本关系.

## 十二. 验收结论

第一期完成的判断标准是:

1. 用户可以用多张产品原图创建一个套图任务.
2. 视觉模型先生成产品档案和 5-6 条镜头提示词.
3. 生图模型按镜头独立生成并保存原始图片.
4. 视觉复核请求只压缩生成图, 产品原图不压缩.
5. 视觉复核只输出通过或人工确认结果, 不自动重新生成.
6. 用户下载、ZIP、素材和画布使用的都是原始生成图.
7. 复核压缩图不会进入正式素材、图片清理或 WebDAV 同步链路.
